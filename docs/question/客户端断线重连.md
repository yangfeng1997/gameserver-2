# 客户端断线重连与坑

## 问题

客户端断线重连，是否可以用 `OnClose` 来做？还是需要一个专门检测断线的回调？

## 结论

可以用 `OnClose` 做重连触发，**不需要专门的"断线检测"回调**——`OnClose` 就是断线回调。这正是 muduo/gnet/Netty 的标准做法（close 回调里 schedule 重连）。但有三个坑要知道。

## OnClose 就是断线信号

客户端 conn 掉线时，eventloop 的 epoll 收到 `EPOLLRDHUP`/`EPOLLHUP`/或读到 EOF → `handleRead` → `teardown` → 触发 `onClose`。覆盖：

- 对端正常 FIN（read 返回 0）→ ✅ OnClose
- 对端 RST / 连接被重置（read 返 ECONNRESET）→ ✅ OnClose
- 你自己 `Close()` → ✅ 也触发（见坑 2）

所以"断线 → OnClose → 里面 `cr.Start()` 重连"成立：

```go
cli.SetOnClose(func(c *network.Conn){
    if stopping { return }      // 坑2：主动关的不重连
    cr.Start()                  // 重拨；Connector 内置退避，失败自动重试
})
```

## 坑 1（关键）：静默断线不会立即触发 OnClose

网线拔了、对端进程被 `kill -9`、中间路由挂了——**没有 FIN/RST 发回来**，TCP 层看不到断。此时 OnClose **不触发**，conn 看起来还活着，直到下一次 send 失败或 keepalive 兜底。

**正解**（二选一或都上，行业标配）：

- **TCP keepalive**：`network.WithTCPKeepAlive(...)`——内核探测，超时后 conn 报错 → OnClose。简单但探测周期默认较长（分钟级），可调。
- **应用心跳**：`conn.RunEvery(几秒, ping)` 发心跳；连续 N 次没收到 pong → `conn.ForceClose()` → OnClose → 重连。**这个最可靠、最常用**，因为应用层能定语义（多久算掉线）。

所以**光靠 OnClose 不够**——要 **OnClose + 心跳/keepalive** 才能覆盖静默断线。OnClose 是触发器，心跳是静默检测器，两者配合。

## 坑 2：主动关闭也会触发 OnClose

你 `cli.Stop()` 或 `conn.Close()` 时，OnClose 照样响。如果里面无条件 `cr.Start()`，**优雅退出时会立刻重连**，停不下来。

正解：加个 `stopping` 标志，OnClose 里判断：

```go
if stopping { return }
cr.Start()
```

## 坑 3：OnClose 里别阻塞、别用旧 conn

- OnClose 在 **eventloop 线程**跑，**不能阻塞**（会卡住该 loop 上所有连接）。只 `cr.Start()`（投递，非阻塞）或 `loop.RunAfter(backoff, reconnect)`。
- OnClose 触发时**旧 conn 已 teardown**（fd 关了、channel 移除了）——**不能复用旧 conn**，重连是**建一个全新 conn**（新 fd、新 Dial）。这和"恢复旧连接"是两回事；要恢复业务状态靠会话恢复（重登录、续 session）。

## 最终

最小可靠客户端重连 = **OnClose 触发 + 应用心跳检测静默断线 + stopping 标志 + Connector 退避**。

- **OnClose 就是断线回调，用它触发重连，不用再造专门的检测回调。**
- 但 OnClose 只能检测"有信号的断线"（FIN/RST/读错）。**静默断线要靠心跳或 keepalive 兜底**——这是必须配的，不是可选。
- 加 `stopping` 标志防主动关时误重连；OnClose 里非阻塞、不复用旧 conn。

库的原语（`OnClose`、`RunEvery`、`ForceClose`、`Connector`）都齐了，不用动库。
