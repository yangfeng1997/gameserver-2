# Q5：conn / session / sessionmgr 行业怎么做

## 标准范式：Session-per-Connection，双向引用，sessionID 作跨服路由键。

**对象关系**：
- **Conn**：传输对象（fd、I/O），归 eventloop 所有。
- **Session**：逻辑/玩家对象（身份、状态），归业务层 sessionmgr 所有。
- **双向链**：`conn.Context = session`（从 conn 找 session）、`session.Conn = conn`（从 session 发数据）。这是 muduo/gnet/游戏服通用做法。

**connID vs sessionID**：
- **connID**：accept 时传输层就有的单调 ID（我们 `Server` 已自动生成，`conn.Name()` = `s-<peer>-<id>`）。可直接当 sessionID 用。
- **playerID**：登录后从 DB/生成器拿，绑到 session（玩家归属）。逻辑身份。
- **实践里常用 connID 当 sessionID**（gate 本地唯一够用）；只有"跨重连保持身份"才需 playerID 持久。

**落法（我们 API）**：

```go
type Session struct {
    ID       uint64          // = connID，作路由键
    Conn     *network.Conn   // 回引用，发包用
    PlayerID uint64          // 登录后绑定
}
type SessionMgr struct {
    mu sync.RWMutex
    m  map[uint64]*Session
}

srv.SetOnConnect(func(c *network.Conn){
    s := sessionMgr.New(c)   // 用 c.Name() 里的 id 或自己的 seq 生成 sessionID
    c.SetContext(s)          // conn → session（SetContext 是 loop 内用）
    // 向后端注册此 sessionID 上线
})
srv.SetOnMessage(func(c *network.Conn, in *network.Buffer){
    s := c.Context().(*Session)
    // 分帧 → cmdID → 查 route：
    //   本地处理 → 投业务队列（带 s.ID）
    //   转发后端 → 消息头盖 s.ID，backendConn.Send(data)  // 同 loop 则 Send 直发
})
srv.SetOnClose(func(c *network.Conn){
    s := c.Context().(*Session)
    sessionMgr.Remove(s.ID)
    // 通知后端 session 下线，后端清理玩家
})
```

**跨服路由的关键（行业标配）**：gate 转发给后端的消息，**消息头里盖 sessionID**。后端处理完回包时也带 sessionID，gate 收到后 `sessionMgr.Get(sessionID).Conn.Send(...)` 转回客户端。**sessionID 是跨服往返的回执凭证**——这样后端不需要知道 conn/fd，只认 sessionID。

**跨线程注意**：sessionmgr 在业务线程；eventloop 在 OnMessage 里 `c.Context()` 读 session 指针（OnConnect 时 set 一次，之后不变 → 读安全）。但 session 的**可变状态**（player 状态）若 loop 和业务线程都碰，需加锁或拆分——**常见做法是 loop 只做"分帧+路由+投队列"，不碰 session 可变状态**，可变状态归业务线程。这正合 gatesvr 的设计。

**行业参照**：
- muduo：`TcpServer` 有内部 conn map；用户用 `TcpConnection::setContext` 挂 session（boost::any）。chat 示例就是这套。
- gnet：`Conn.SetContext`/`SetSafeContext`，完全对应。
- skynet/KBEngine 等：gate 分配 session 句柄，转发消息盖句柄，后端按句柄回 gate。一模一样的思路。
